# OpenAPI precision sample

## Method and provenance

One labeller (Devin), non-blind labels: the labeller saw the checker verdict, docs and spec. No independent adjudicator or blind-admission claim.
No rule, policy, fixture or documentation-source changes were made. No SDK, live API, git log or blame evidence was used; no rename/removal history is inferred.
Population: 814 HEAD findings, exactly rechecked against Phase C HEAD on this run. The population is identical to the openapi-field-exists subset of after-round2.json.
Seed: **20261111**; Python random.Random. Sort by (path, line, evidence), shuffle once, scan shuffled findings accepting at most three per page, stop at 50. This is page-capped rejection sampling (28 pages, maximum 3/page), not project-proportional or an unbiased estimate of all 814 findings. Do not generalize this exploratory sample precision to the full population.
The sampling paths are corpus-relative in JSONL. JSON pointers in checked_sources use standard RFC 6901 escaping.
Population report SHA-256: `4cc875de2e41e2a9955dfe9c13a2e6a37058078a346275d57658fe92c1582d56`.
OpenAPI snapshot SHA-256: `4d548c71bd296e21d511a256870802dc0b7c42b61d5fcbf98390aebfe7942225`.
Nearest inventory names are string-distance suggestions, not proposed fixes. Absence means a recursive scan found no structural properties/enum member for that exact token. Explicitly checked endpoint schemas/examples/parameters and docs passages are preserved in each JSONL row with content hashes.
For nested/repeated names the inherited finding line can point to the first key in the JSON payload rather than the pointer-specific occurrence (notably #15 and #26). The JSON pointer was resolved against the containing source example as an additional check. This location-quality issue does not by itself make the vocabulary verdict false.

Unclear is excluded from the denominator, not counted as a false positive or a true positive. A spec-gap label means the documentation/spec evidence makes a real field appear likely, not that production behavior was tested.

## False-positive patterns (listed only; nothing fixed)

| Pattern | Sample findings | Evidence |
|---|---:|---|
| Cross-object status enum applied to unconstrained status strings | 12 | posted is explicitly documented in the Ledger Transaction request and response; approved is the Payment Order response example. |
| address_types values documented in a description/string array, not the global enum bag | 2 | Legal Entity individual/child address schemas explicitly permit residential. |
| JSON-encoded spec examples ignored by the property inventory | 5 | Document source=customer exists in the /identifications POST 201 example; /documents also accepts a source filter. |
| User-chosen variable map keys mistaken for API property names | 1 | The tutorial says variables is a name -> (object_type, query) map; wallet_account is a binding. |

Webhook envelope fields in this sample were not automatically called false positives: their repeated MT docs support likely schema gaps, but no corresponding typed notification-envelope response was found. Null/empty sample fields, solitary examples, and similar names in unrelated endpoints were left unclear when no stronger evidence settled the contract.
